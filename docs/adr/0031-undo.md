# 0031. Undo: transactions of entity snapshots, identified by scene ids

- Status: Accepted
- Date: 2026-09-26
- Follows: [ADR 0029](0029-scene-format.md) (`SceneId`), [ADR 0017](0017-ecs.md)

## Context

CLAUDE.md §12: everything in the editor is undoable, every action is a command inside
a transaction, and there is a global history with a panel. Actions include:
- field edits (often continuous: drags);
- spawning and deleting subtrees;
- reparenting and reordering;
- adding and removing components.

## Options

1. **Command pairs** (Godot `UndoRedo`): every action registers a do and an undo
   method. It is flexible, but every tool has to write and maintain its inverse, and a
   missed case corrupts history silently.
2. **Whole-world snapshots** (Blender's memfile undo). Simple and exact, but memory and
   time grow with the scene, not with the change.
3. **Per-object state recording** (Unreal transactions, Unity `Undo.RecordObject`;
   chosen). Before changing an object, the tool records it. The system stores the
   object's state before and after and restores either one. Tools write no inverse
   code, and cost is proportional to what changed.

## Decision

- **`engine_editor::History`:**
  - `begin(name, merge_key)`;
  - `touch(world, entity)` before changing an entity;
  - `touch_new` right after spawning one;
  - `touch_subtree` before moving a subtree;
  - `delete_subtree` to delete a subtree;
  - `commit(world)` to finish, or `cancel(world)` to abandon;
  - `undo` and `redo`;
  - `steps()` and `redo_steps()` for the history panel.
- **Entity state:**
  - every plain-data component as bytes;
  - parent and index among the siblings (the `Parent` and `Children` links are
    rebuilt from these, not copied).
  - Non-plain-data components are counted in `skipped_non_pod()` and not recorded.
    Editor-facing components are plain data today.
- **Identity:**
  - entities are keyed by `SceneId`; `touch` assigns one if missing;
  - a deleted entity restored by undo gets a new `Entity` handle but the same id;
  - entity references inside components are stored as scene ids (found through
    reflection) and resolved again on restore.
  - `delete_subtree` also records every entity that refers into the deleted subtree,
    so undo restores those references instead of leaving them dangling.
- **Restore order:**
  1. existence (spawn or despawn, detached first);
  2. components;
  3. hierarchy: detach every moved entity, then re-attach by ascending sibling index
     with `World::set_parent_at`.
- **Merging:** consecutive commits with the same merge key become one step, keeping the
  first "before" and the last "after". A step whose net effect is nothing disappears.
  Commits that change nothing are not recorded.
- **Memory:** a byte budget (default 256 MiB); the oldest steps are dropped beyond it.
- **ECS additions:** `World::component_ids_of`, `Components::layout`,
  `World::set_parent_at`, `World::child_index`.

## Verification

`crates/engine_editor/tests/undo.rs` checks each state against the scene text
(`engine_scene::save`):
- create, edit, reorder, delete and back, then redo;
- drag merging; net-zero merges; no-op commits;
- cancel;
- the budget;
- a randomized walk: 4 seeds × 300 random actions (spawn, reparent, delete subtree,
  edit, reparent at an index, add a component with an entity reference). Every undo and
  every redo matches the recorded text exactly.

## Consequences

- Tools write no inverse code: touch, change, commit.
- References from other entities into a deleted subtree are restored only through
  `delete_subtree`. A tool that despawns with `World::despawn` after `touch` alone
  would leave them dangling after undo.
- `delete_subtree` scans the world for references (linear in entities). It is fine for
  editor actions. A reverse-reference index can replace the scan if profiles show it.
- Non-plain-data components (future strings, script state) need a serialization hook
  before they can take part.
