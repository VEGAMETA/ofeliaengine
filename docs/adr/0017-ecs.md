# 0017. ECS / scene model

- Status: **Proposed**: awaiting the team's decision (CLAUDE.md §3: the ECS model is an
  irreversible decision the humans make)
- Date: 2026-09-26
- Research: [docs/research/ecs.md](../research/ecs.md); harness `bench/ecs-compare`

## Context

CLAUDE.md §17 step 4 starts with the ECS / scene model. Serialization, the editor skeleton
(scene, inspector, undo, command palette) and scripting (step 5) build on it. §13 lists the
candidates and criteria.

## Options

1. **`bevy_ecs` as a library.**
   - The richest Rust option: change detection, observers, relationships, queries with
     filters, reflection.
   - It fixes our toolchain to its cadence (0.19 needs Rust 1.95) and brings breaking
     upgrades.
   - Its task pool sits beside our job system.
   - It iterates 1.8× slower than the prototype in our measurement, because of the
     per-access change ticks.
2. **`hecs`.**
   - Small and stable, fast structural changes.
   - Nearly everything the editor and scripting need would be built on top.
   - No run-time components.
   - 2.7× slower iteration.
3. **flecs through `flecs_ecs`.**
   - The most complete feature set (relationships, prefabs, reflection, explorer).
   - A C core behind FFI: structural operations 4.7–10× slower through the bindings.
   - Not the Rust core CLAUDE.md §1 asks for.
4. **Our own archetype ECS (`engine_ecs`).**
   - The prototype already matches or beats all three on every measured scenario.
   - Full control over allocations, threading, determinism, editor integration and
     run-time components.
   - Costs our time for the features the others already have.

## Measurements

ref-1 (Ryzen 7 7700), µs, lower is better. The full table is in the research note:

| spawn 10k × 4 | 534 | 836 | 958 | 5 582 |
| iterate 10k | 4.3 | 8.9 | 7.6 | 5.8 |

| add + remove, 10k | 398 | 435 | 791 | 1 125 |
| random get 10k | 93 | 201 | 88 | 237 |

## Recommendation (for the team to accept or change)

**Option 4, our own archetype ECS**, with these design points:
- **Storage:** archetypes with structure-of-arrays columns (as in the prototype),
  generational entities, cached add and remove edges.
- **Components are run-time descriptors:** layout, drop and a reflection vtable. Rust
  types register through a derive; Luau scripts register theirs the same way. Editor,
  serialization and scripting share one metadata source (§10, §12).
- **Change tracking is coarse by default:**
  - a per-column "written in frame N" stamp, set when a query declares write access;
  - optional per-row change bitsets for the components that need fine tracking (network
    replication, editor inspectors);
  - not a tick per access.
- **Structural changes during parallel work** go into per-job command buffers in frame
  arenas and are applied at sync points in a deterministic order. The same log feeds
  editor undo and redo (§12: "every action is a command inside a transaction").
- **Deterministic by construction:** stable entity allocation and archetype iteration
  order within a build, for rollback and lockstep (§13).
- **Queries:** cached archetype matches, typed slice iteration, parallel chunks through
  `engine_core::jobs`.
- **Hierarchy:** `Parent` / `Children` components that do not fragment archetypes. Flecs'
  pair-based relationships are a later option.

### Questions for the team

1. Accept option 4 (own ECS), or prefer `bevy_ecs` (features sooner, upstream churn)?
2. Is determinism (identical results for the same inputs on the same build and CPU class)
   a requirement for the scene model from day one, or only for physics?

## Consequences (if option 4 is accepted)

- A new crate `engine_ecs`: the prototype is its starting point, tested against the
  harness scenarios.
- **Order of work:**
  1. core storage and queries;
  2. commands;
  3. change tracking;
  4. hierarchy;
  5. reflection derive;
  6. serialization to text scenes (§13);
  7. editor skeleton with undo.
- `bench/ecs-compare` stays as the regression reference against the external ECSs.
