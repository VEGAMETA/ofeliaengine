# 0017. ECS / scene model

- Status: Accepted
- Date: 2026-09-26
- Research: [docs/research/ecs.md](../research/ecs.md); harness `bench/ecs-compare`
- Related: [ADR 0019](0019-networking-model.md) (the networking model sets requirements
  on the ECS)

## Context

CLAUDE.md §17 step 4 starts with the ECS / scene model. Serialization, the editor skeleton
(scene, inspector, undo, command palette) and scripting (step 5) build on it. §13 lists the
candidates and criteria.

The team decided two questions this ADR originally left open:
1. **Our own ECS,** not `bevy_ecs`.
2. **Determinism of the scene model from day one,** because the engine will need
   Source-style networking (ADR 0019): prediction and rollback need the same results from
   the same inputs, and cheap save and restore.

## Options

1. **`bevy_ecs` as a library.**
   - The richest Rust option: change detection, observers, relationships, queries with
     filters, reflection.
   - It fixes our toolchain to its cadence (0.19 needs Rust 1.95) and brings breaking
     upgrades.
   - Its task pool sits beside our job system.
   - It iterates 1.8× slower than the prototype, because of the per-access change ticks.
   - Determinism is not an upstream goal.
2. **`hecs`.**
   - Small and stable, fast structural changes.
   - Nearly everything the editor, scripting and rollback need would be built on top.
   - No run-time components.
   - 2.7× slower iteration.
3. **flecs through `flecs_ecs`.**
   - The most complete feature set.
   - A C core behind FFI: structural operations 4.7–10× slower through the bindings.
   - Not the Rust core CLAUDE.md §1 asks for.
4. **Our own archetype ECS, `engine_ecs`** (chosen).

## Decision

`engine_ecs`, built for speed, determinism and rollback.

### Storage

- **Archetypes** (one per component set) store rows as structure of arrays in chunks.
- **Chunks grow with the archetype:**
  - its first chunk is 16 KiB, the next two 64 KiB, the rest 256 KiB;
  - small archetypes stay small, and large ones iterate at memory bandwidth (measured
    below).
- **Chunks come from a per-world pool** of 256 KiB slabs: steady-state spawning and
  despawning never reach the global allocator.
- **Rows are dense:** removal moves the archetype's last row into the hole.
- **Generational entity handles.** Allocation is deterministic: the most recently freed
  slot first.
- **Structural changes** follow cached add and remove edges between archetypes.

### Components

- **Rust components** implement `Component` (`component!`, `pod_component!`).
- **Plain-data components** carry a compile-time proof (`bytemuck::Pod`). They are
  copied, hashed and rolled back as bytes.
- **Scripts register components at run time** (`World::register_dynamic`) with a layout,
  drop function and name. Editor, serialization and scripting will share this metadata
  (§10, §12).

### Queries

- **`QueryState<Q, F>`** caches its matching archetypes. Fetches: `&T`, `&mut T`,
  `Entity`, `Option<_>`, tuples. Filters: `With`, `Without`, `Changed`.
- **Iteration forms:**
  - per entity;
  - per chunk (the arrays themselves, for SIMD);
  - as an iterator;
  - in parallel over chunks on `engine_core::jobs`.
- **Aliasing** (`&mut T` with another access to `T`) is rejected when the query is
  created, not on every iteration.

### Change tracking

- **One change tick per chunk and component,** stamped by writing queries (one store per
  chunk) and direct writes.
- **No per-entity ticks:** gameplay code pays nothing per write. Replication compares
  quantized values inside changed chunks (ADR 0019).

### Hierarchy

- **`Parent` and `Children`** are plain-data components forming an intrusive sibling
  list: the child holds its parent and neighbours, the parent the first and last child
  and the count.
- **Links are snapshotted and hashed like other state.** Children keep insertion order,
  and attaching or detaching is O(1).
- **Cycles are rejected.** `despawn_recursive` removes a subtree.
- **No archetype fragmentation by parent.** Parent-keyed relationships, as in flecs,
  split archetypes per parent.

### Commands

- **Commands** record spawns, inserts, removals and despawns into a reusable buffer.
- `World::apply` performs them in recording order; buffers from parallel jobs are
  applied in job order.

### Determinism (from day one)

- **Canonical iteration order.** Queries iterate archetypes sorted by the stable names of
  their components, not by creation order. A rolled-back peer that created archetypes in
  a different order still iterates like one that did not.
- **`World::save` / `World::restore`** copy every row, the entity allocator and the
  simulation tick into a reusable `Snapshot`. Restoring and re-simulating gives the same
  state hash as the first run (tested).
- **`World::state_hash`** hashes the tick, allocator and all plain-data components in
  canonical order, independent of chunk sizes. Its hasher (`engine_core::hash::StateHasher`)
  is four-lane, multiply-rotate.
- **Change ticks are bookkeeping, not state.** A restore marks everything changed.
  Deterministic game logic must not depend on `Changed` filters.

## Measurements

### Against the candidates

Harness `bench/ecs-compare`, cloud container (4 vCPUs, noisy, **not reference**), µs,
median:

| scenario | prototype | hecs | bevy_ecs | flecs | engine_ecs |
|---|---:|---:|---:|---:|---:|
| spawn 10k × 4 components | 903 | 1 254 | 1 376 | 12 961 | 224 |
| iterate 10k: position += velocity | 7.7 | 21.1 | 13.7 | 10.3 | 8.5 |
| fragmented: 26 archetypes × 20 | 0.2 | 0.7 | 0.4 | 1.0 | 0.3 |
| add + remove a component, 10k | 602 | 683 | 1 204 | 2 960 | 736 |
| random get of 10k (of 100k) | 175 | 335 | 176 | 790 | 170 |

- That run had 16 KiB chunks throughout.
- Its 1M iteration (4 156 µs, 3× the prototype) led to the size classes.

### The chunk size experiment

`engine_ecs` benches, iterate 1M entities (108-byte rows), µs:

| chunk size | 16 KiB | 64 KiB | 256 KiB | classes 16 → 64 → 256 KiB | prototype (one array per component) |
|---|---:|---:|---:|---:|---:|
| position += velocity | 4 253 | 1 643 | 1 237 | 1 344 | 1 372 |

- **Why 16 KiB chunks are slow:** with 16 KiB chunks each component array is about
  1.7 KiB (28 cache lines), too short for the hardware prefetcher to ramp up. The loop
  becomes latency-bound.
- **The size classes fix it** without making small archetypes large.

### engine_ecs benchmark

`cargo bench -p engine_ecs --bench ecs`, same container:
- **Spawn 10k × 4 components:** 243 µs into pooled chunks (24 ns per entity); 640 µs
  into a new world (page faults of fresh memory).
- **Despawn 10k:** 212 µs.
- **Iterate:**
  - 10k: 7.8 µs;
  - 1M: 1 344 µs;
  - 1M in parallel on 4 threads: 720 µs.
- **Add + remove, 10k:** 830–900 µs.
- **Snapshot of 100k entities (10.8 MB):** save 830–980 µs, restore 840–990 µs, state
  hash 640–790 µs.

ref-1 numbers come from the bench workflow on the PR that implements this ADR.

### Correctness

Unit tests, all passing:
- structural changes with drop accounting;
- every query form and filter;
- change tracking per chunk;
- commands, including dropping unapplied buffers;
- components larger than a chunk, 64-byte-aligned and zero-sized;
- dynamic components;
- identical call sequences giving identical hashes;
- iteration order independent of archetype creation history;
- rollback and re-simulation matching the first run;
- parallel iteration matching sequential;
- 60 000 entities across all chunk classes, despawned in scattered order and restored.

**Miri** (Stacked Borrows) runs the unit tests with `-Zmiri-deterministic-floats`.
- It found a pointer-provenance bug in `engine_core::jobs`: job references derived from
  a pointer to the header field only. The bug is fixed in the same change.
- Without that flag, the parallel-equals-sequential test fails under Miri. Miri
  deliberately perturbs `sin` and other platform math functions, as different machines'
  math libraries may.
- The lesson for cross-machine lockstep: simulation code needs deterministic
  transcendental functions (CLAUDE.md §8). The dev guide says so.

## Consequences

- **Follow-ups, in order:**
  1. reflection derive shared with scripting (§10) and the network field metadata
     (ADR 0019);
  2. serialization to text scenes (§13; the on-disk format is a team decision);
  3. editor skeleton with undo, fed by the command log;
  4. a system scheduler on the job system (access sets from `Fetch::register`) — done, ADR 0026;
  5. transform propagation over the hierarchy.
- **Possible later optimizations:**
  - incremental snapshots (copy only chunks written since the last save);
  - per-block change versions inside 256 KiB chunks, if replication needs finer
    granularity.
  - **Iterating 1M entities: gap closed from 46 % to about 10 %** against one
    contiguous array per component.
    - **Before:** 600–680 µs against 465–478 µs on ref-1.
    - **Prefetch is not the answer:** software prefetch of the next chunk's arrays was
      measured and gave nothing (604 µs).
    - **The layout study** (`bench/ecs-compare`, `p += v` over 1M rows) found two
      causes:
      - short column runs in 256 KiB chunks with wide rows (591 µs, against 473 µs for
        1 MiB chunks and 458 µs for whole columns);
      - "4K aliasing": two same-size columns starting a near multiple of 4 KiB apart
        (24-byte rows got slower in bigger chunks, 604–751 µs).
    - **Fix:**
      - chunks grow 16 KiB, 64 KiB ×2, 256 KiB ×4, then 1 MiB;
      - in chunks of 64 KiB and more, column *c* starts at *c* · 4096 / *n* within a
        page.
      - Now 558 µs against the prototype's 507 µs in the same run.
    - **Random `get`** measured equal to the prototype on a later run (92 µs both); the
      earlier 123 µs was noise.
    - **Coarser `Changed` filter for large archetypes:** 1 MiB chunks make it coarser
      there (one version per ~10k rows for 100-byte rows). Per-block versions remain the
      option if replication needs it.
- `bench/ecs-compare` stays as the regression reference. It now includes `engine_ecs`.
