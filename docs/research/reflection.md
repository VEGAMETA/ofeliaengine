# Reflection: one description of every type's fields

Checked on 2026-09-26.

Four subsystems need to see inside components and other engine types:
- **Text serialization** of scenes and settings (§13);
- **The editor's inspector** (§12): a widget per field, ranges, tooltips, undo;
- **Luau scripting** (§10): property access by name and generated `.d.luau` types;
- **Networking** (ADR 0019): per-field quantization for snapshots.

One description per type should serve all four. It must be fast enough for the
network path, which runs over thousands of entities per tick.

No code was copied. Godot and bevy_reflect are MIT (bevy also Apache-2.0); Unreal is
studied as a product.

## How they work

- **Godot:**
  - every exposed property is a `PropertyInfo` registered with `ClassDB`;
  - reads and writes go through `Object::get` / `set` with `Variant` values, a tagged
    union, by name;
  - hints drive the inspector;
  - usage flags decide what is saved, shown or networked.
  - Flexible and uniform, but every access is a string-keyed virtual call plus a
    `Variant` conversion.
- **bevy_reflect:**
  - a derive generates `TypeInfo`: struct, tuple, enum, list or map info with field
    names and types;
  - it also generates `Reflect` trait implementations that return `&dyn PartialReflect`
    per field;
  - serialization goes through a type registry and serde;
  - custom attributes are supported.
  - Complete, but field access is dynamic dispatch per field, and values are boxed when
    built dynamically.
- **Unreal:**
  - UHT generates property tables with offsets from `UPROPERTY` macros;
  - serialization, replication, the editor and Blueprints read and write fields directly
    at those offsets;
  - metadata specifiers drive the editor and replication conditions.
  - This is the fastest of the three and has served all four uses for decades.

## What we take

**Unreal's approach, in Rust: static field tables with offsets, generated by a derive.**
- **`TypeInfo`:**
  - name, size, alignment, and a kind: struct (fields), C-like enum (variants with
    values), primitive, fixed array, or opaque;
  - each field: name, byte offset (`core::mem::offset_of!`), its type's `TypeInfo`, and
    attributes.
- **Attributes, one namespace for the four users:**
  - `range` and `step` (inspector, script validation);
  - `tooltip` (inspector, `.d.luau` docs);
  - `hidden`, and `skip` for things not saved;
  - `net(quantum = 0.01)` or `net(skip)` (replication, ADR 0019);
  - `rename` (stable file names across code renames).
- **Access is pointer arithmetic,** not dynamic dispatch. Reading a field is one add and
  one load. The network path quantizes fields straight from chunk memory, and
  serialization walks the table.
- **Script-defined components** get the same `TypeInfo` built at run time (with owned
  names). Rust and Luau components are indistinguishable to the four users.
- **Engine math types** (vectors, quaternions, matrices, colors) get hand-written tables
  in `engine_reflect`, with widget hints (color picker, rotation in degrees).
- **Not taken:**
  - reflection of `Vec`, `HashMap` or trait objects: components that need them are
    opaque to the inspector and serialize through an explicit hook;
  - bevy's dynamic structs;
  - Godot's `Variant` on hot paths (scripts get a tagged value type only at the Luau
    boundary).

## What stays open for the team

The **on-disk text format** that serialization writes (scenes, prefabs, settings, input
maps) is one of CLAUDE.md's irreversible decisions. Options:

1. **A line-oriented format of our own,** in the spirit of Godot's `.tscn`:
   - one section per entity with a stable id, one `component.field = value` line per
     value, sorted;
   - merges and diffs are line-local, and the parser is small and fast;
   - no dependency.
2. **RON** (Rust Object Notation, used by Bevy scenes). Nested and expressive, readable
   by Rust developers; merges are worse on deeply nested values; serde dependency.
3. **TOML or JSON.** Widely known. TOML is awkward for deep nesting; JSON has no
   comments and diffs poorly.

The recommendation is option 1. Reflection works the same under all three, so the
reflection work can start before the choice.
